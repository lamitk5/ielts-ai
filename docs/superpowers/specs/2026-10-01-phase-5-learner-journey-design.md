# IELTS AI Tutor — Phase 5 Learner Journey Design

Status: architectural design only. This document does not change product code,
database migrations, runtime configuration, or deployment configuration.

## 1. Purpose

Phase 5 makes the authenticated learner journey coherent from first setup to
targeted daily practice:

`ONBOARD → DIAGNOSE → PLAN → PRACTICE → REVIEW MISTAKES → RETRY → MOCK TEST →
TRACK PROGRESS`.

It builds on the Phase 4 submission/result contract and the existing Phase 2
adaptive profile/roadmap. It does not create fake personalization, official
placement, or a second learning engine.

## 2. Scope

Phase 5 designs:

- onboarding goals and editable learner preferences;
- a safe diagnostic flow with explicit confidence/insufficient-data states;
- Today's Adaptive Plan with evidence-backed reasons;
- an owned Error Notebook over real mistake evidence;
- IELTS-style, explicitly non-official Mock Test mode;
- data-driven Progress page;
- real learning-content search integration;
- saved practices;
- profile/settings completion;
- APIs, data ownership, state machines, performance, testing, and additive
  migration strategy.

Phase 5 consumes Phase 4 submissions/results. It does not duplicate scoring,
Writing evaluation, Speaking/STT, Tutor, Practice Generator, or adaptive
profile logic.

## 3. Onboarding

The first authenticated learner sees a resumable setup flow with:

- current IELTS level as self-report;
- target band;
- target exam date, optional;
- weakest perceived skill;
- daily study minutes;
- study days per week.

The learner may Skip and Edit later. The values are stored as preferences and
goal inputs, separately from evidence-backed Phase 2 profiles. The UI labels
self-report as a goal/belief, never as measured ability.

Completion is idempotent and owner-scoped. A partial setup can be resumed after
refresh. Updating a goal creates a new preference version or audit timestamp;
it does not rewrite historical diagnostic or submission results.

## 4. Learner Goals

Goal data has:

- owner ID;
- target band, validated to the configured IELTS band range;
- optional exam date that cannot be interpreted as a score guarantee;
- perceived weakest skill;
- daily minutes and days per week with bounded values;
- locale/timezone where needed for daily-plan display;
- created/updated timestamps and version.

No goal is considered evidence. If the learner gives no goals, the system
shows a neutral setup invitation and continues to provide general approved
practice.

## 5. Diagnostic Test

The diagnostic is a bounded, resumable baseline rather than an official exam:

- mini Reading using deterministic approved questions;
- mini Listening using only configured media; if media is unavailable, label
  the capability honestly and do not simulate it;
- one Writing task evaluated as Band ước lượng only when AI evaluation is
  available;
- Speaking self-assessment or text-only safe option when real audio/STT is not
  enabled.

The diagnostic is implemented through the Phase 4 submission engine with a
diagnostic session reference and a fixed diagnostic content/version snapshot.
It must support skip, resume, submit, partial grading, and retry policy.

## 6. Diagnostic Evidence

Diagnostic output is an `Estimated starting profile`, not an official band
placement. It contains per-skill evidence, source submissions, confidence,
missing-capability flags, and initial recommendations.

Confidence states:

- `SUFFICIENT_FOR_INITIAL_GUIDANCE`;
- `LIMITED_EVIDENCE`;
- `INSUFFICIENT_DATA`;
- `NOT_ATTEMPTED`.

The diagnostic must never overwrite a stronger subsequent Phase 2 profile with
weaker self-report. A diagnostic result is one evidence source with policy-
defined weight and audit references.

## 7. Today's Adaptive Plan

The dashboard centerpiece is `Hôm nay học gì?`. The plan is generated by the
existing Phase 2 roadmap/profile services plus Phase 5 goal and availability
inputs. It returns at most 3–5 items, each containing:

- skill;
- approved practice or roadmap item;
- activity type/question type;
- estimated minutes;
- priority;
- evidence-backed reason;
- source issue/profile/roadmap reference;
- state (`NOT_STARTED`, `IN_PROGRESS`, `COMPLETED`, or `SKIPPED`).

Example reason: “Reading — Matching Headings · 15 phút · xuất hiện lỗi ý chính
ở 2 lượt gần đây.” A reason is omitted or replaced with an honest
`Cần thêm dữ liệu` state when evidence is insufficient.

The service must not recommend content that is not approved and visible. It
does not claim that a recommendation guarantees a band outcome.

## 8. Error Notebook

`Sổ lỗi sai` is a learner-owned projection over `learning_mistakes`, question
results, explanations, and trusted retries. It shows:

- skill;
- practice/version and question/task;
- learner answer;
- correct answer after submission;
- mistake type and confidence;
- evidence and explanation;
- times repeated;
- first and last seen;
- status (`OPEN`, `MONITORING`, `RESOLVED`, or `UNKNOWN`).

Actions:

- `Làm lại`;
- `Hỏi Tutor`;
- `Bài tương tự`;
- `Đánh dấu đã hiểu`.

One successful retry does not permanently resolve a recurring issue unless the
existing policy has enough independent evidence. “Đã hiểu” is a learner action
and may become a signal, but it cannot erase source mistake history or alter a
score.

The first implementation should reuse `learning_mistakes` and its evidence
fields. Add a separate notebook table only if user notes, acknowledgement
history, or retention requirements cannot be represented without corrupting
the adaptive record. The projection must remain bounded and paginated.

## 9. Full Mock Test

Mock Test is an IELTS-style product mode, explicitly not an official IELTS
exam. It contains Listening, Reading, Writing, and Speaking sections with:

- session and section identity;
- fixed content/version snapshot;
- section navigation;
- preparation/section/test timer;
- autosave and resume policy;
- time warnings;
- final submission;
- partial and full grading states;
- a result shell linked to Phase 4 results.

Reading and Listening are deterministic. Writing shows Band ước lượng when real
AI evaluation exists. Speaking follows the safe manual/text/audio boundary and
does not invent pronunciation or fluency scoring.

If an overall estimate is ever shown, it requires a separately approved,
versioned policy and the same explicit non-official disclaimer. Without that
policy, show section results and a completion summary only.

## 10. Mock Test State Machine

### 10.1 Session states

- `CREATED` → `IN_PROGRESS`;
- `IN_PROGRESS` → `PAUSED`, `SUBMITTED`, or `EXPIRED`;
- `PAUSED` → `IN_PROGRESS`, `SUBMITTED`, or `EXPIRED`;
- `SUBMITTED` → `PARTIALLY_GRADED`, `FULLY_GRADED`, or `FAILED`;
- `PARTIALLY_GRADED` → `FULLY_GRADED` or `FAILED`;
- `FULLY_GRADED` and `EXPIRED` are immutable terminal views.

Each section has its own state and server-side finalization marker. A section
cannot be submitted twice with different content. A refresh reopens only a
server-authorized resumable session, never a finalized section.

### 10.2 Timer and resume policy

The server stores start/pause/resume timestamps and computes elapsed time. The
browser timer is a display. A configured grace policy handles a lost connection
without extending a finalized session. On expiration, the server records the
last durable snapshot and transitions according to the session policy.

## 11. Progress Page

The existing Progress surface becomes data-driven without a visual redesign.
It uses bounded summary endpoints for:

- overview;
- four-skill progress;
- 7-day trend;
- 30-day trend;
- common mistakes;
- roadmap;
- recent submissions;
- Error Notebook summary;
- diagnostic baseline;
- target/goal progress.

Every chart/card is built from authenticated learner data. A new learner sees
meaningful empty states such as “Chưa có đủ dữ liệu để tạo xu hướng”, not
invented numbers. Band ước lượng labels and evidence confidence remain
visible wherever applicable.

## 12. Search Integration

The existing Search route becomes a real, owner-scoped learning search over:

- active approved practice;
- question types;
- topics;
- Writing prompts;
- Speaking topics;
- the current learner's submission history.

Search results carry a type, title, skill, route/action, and visibility reason.
They never expose unapproved Phase 3 content, another learner's submission,
admin review data, answer keys before submission, or raw private Tutor context.

Search ranking is deterministic initially: exact title/skill/topic match,
approved visibility, then recent learner relevance. No LLM is required for
search.

## 13. Saved Practices

`Saved Practices` is a small owner-scoped feature:

- save an active approved published practice/version;
- unsave it idempotently;
- list with pagination and skill filter;
- remove an entry when the learner requests it;
- preserve historical submission links even if a newer publication replaces
  the saved version.

The server revalidates visibility on list and start. A hidden/deactivated
practice is shown as unavailable with no new attempt action; it is not silently
replaced by another set.

## 14. Profile/Settings

Extend the current preferences/profile surfaces without duplicating auth tables.
Support:

- display name and avatar reference;
- target band and exam date;
- daily goal and study schedule;
- Tutor preferences;
- theme, language, density, animation, and existing learning preferences;
- change password through the existing auth service;
- logout.

Profile identity belongs with the current user/auth model. Learning goals and
schedule belong in the learner-goal/profile extension. UI preferences remain in
`user_preferences`. Do not store passwords or provider credentials in the new
learner tables.

## 15. Data Model

### 15.1 Reuse first

Reuse:

- `app_users`, `auth_sessions`, and current preferences;
- Phase 4 canonical submissions/results;
- `learning_events`, `learning_mistakes`, profiles, issues, and roadmaps;
- approved `practice_catalog_publications` and exact practice versions;
- existing Tutor conversation/context ownership.

### 15.2 Minimal new concepts

1. `learner_onboarding_profiles`: self-reported goals, schedule, completion,
   version, and timestamps; separate from evidence profiles.
2. `diagnostic_sessions`: owner, diagnostic content/version, state, started,
   submitted, and completion policy.
3. `diagnostic_results`: per-skill evidence/confidence and source submission
   references; immutable result versions.
4. `mock_test_sessions`: owner, mock definition/version, state, timing,
   idempotency, and result status.
5. `mock_test_sections`: session, skill/order, fixed practice references,
   state, timing, and Phase 4 submission reference.
6. `saved_practices`: owner, published set/version, saved timestamp, and
   unique owner/version constraint.

Today's Plan is a bounded service projection over Phase 2 roadmap/profile,
goals, approved catalog, and recent submissions. Error Notebook initially is a
projection over `learning_mistakes` plus owned question results. This avoids
creating duplicate tables for data the current model already owns.

### 15.3 Ownership, indexes, audit, retention

Every new row has owner foreign key and owner/status/time indexes. Diagnostic
and Mock Test state changes are auditable and idempotent. Saved practices have
an owner/version unique key. Deleting a learner removes their goals,
diagnostic results, mock sessions, saved practices, and derived notebook view
according to the established retention policy; published practice provenance
is retained independently.

## 16. APIs

| Method | Route | Purpose |
| --- | --- | --- |
| GET/PUT | `/api/me/onboarding` | Read or save owner-scoped goals/preferences. |
| POST | `/api/me/onboarding/complete` | Mark setup complete or skipped idempotently. |
| POST | `/api/diagnostics` | Start a version-pinned diagnostic. |
| GET | `/api/diagnostics/{id}` | Resume owned diagnostic. |
| POST | `/api/diagnostics/{id}/submit` | Finalize diagnostic through Phase 4 submissions. |
| GET | `/api/diagnostics/{id}/result` | Read estimated starting profile/confidence. |
| GET | `/api/me/today` | Get 3–5 evidence-backed plan items. |
| POST | `/api/me/today/{itemId}/complete` | Complete an owned plan item through roadmap policy. |
| GET | `/api/me/error-notebook` | Paginated owned mistake projection and filters. |
| POST | `/api/me/error-notebook/{id}/acknowledge` | Record learner acknowledgement without deleting evidence. |
| POST | `/api/mock-tests` | Start a version-pinned IELTS-style mock. |
| GET | `/api/mock-tests/{id}` | Read/resume owned mock session. |
| PUT | `/api/mock-tests/{id}/draft` | Save session/section progress. |
| POST | `/api/mock-tests/{id}/submit` | Finalize mock session idempotently. |
| GET | `/api/mock-tests/{id}/result` | Read partial/full result state. |
| GET | `/api/search` | Search approved content and the current user's history. |
| POST/DELETE | `/api/me/saved-practices/{publishedSetId}` | Save or unsave approved content. |
| GET | `/api/me/saved-practices` | List saved practices with pagination. |
| GET/PUT | `/api/me/profile` | Read/update learner-facing profile fields. |

All routes derive user identity from the session. Client-supplied owner IDs,
scores, evidence, admin states, or recommendation reasons are ignored.

## 17. Adaptive Learning Integration

Phase 5 calls existing Phase 2 services for profile, issues, trend, and
roadmap. It does not recalculate a separate weakness score in the frontend.

Inputs to Today's Plan are:

- trusted Phase 4 graded events and mistake evidence;
- current Phase 2 roadmap/issue states;
- onboarding target and available time;
- approved catalog availability;
- current in-progress submission state.

Recommendations include evidence references and reason codes. Missing evidence
produces a diagnostic/general-practice state, not fabricated personalization.
Completing a plan item delegates to the existing roadmap completion policy and
does not directly edit a band or weakness count.

## 18. Assessment Integration

Diagnostic and Mock Test sections are wrappers around Phase 4 submissions:

- Reading/Listening use server deterministic scoring;
- Writing creates immutable versions and AI evaluation states;
- Speaking uses real audio/manual/text-only boundaries;
- result links point to the common result shell;
- adaptive updates occur only from trusted graded results;
- all practice references are exact approved versions.

No Phase 5 UI is allowed to calculate a score from browser answers or infer an
official placement from diagnostic completion.

## 19. Security

The server enforces:

- owner isolation for onboarding, diagnostics, plans, mistakes, mock sessions,
  saved practices, profile, and Tutor context;
- no reading another learner's submissions, scores, drafts, audio, notebook, or
  plan reason;
- role-protected admin data remains outside learner search/progress;
- approved visibility before saving or starting practice;
- immutable diagnostic/mock version references;
- server-side timer/state/idempotency checks;
- rate limits and pagination bounds;
- safe error categories with no raw AI/provider/database details.

## 20. Performance

Dashboard uses one bounded summary/read-model request or a server-composed
summary, not a client waterfall over all history. Plan items are capped at five.
Notebook, submissions, search, and saved practices are paginated with bounded
filters. Trends aggregate by date window in the backend. Mock sections load on
demand while the current section remains locally responsive. Tutor history is
never loaded as part of the dashboard by default.

## 21. UX

The Academic Luxury shell remains unchanged. The learner flow uses a clear
priority order:

1. Continue Learning;
2. Hôm nay học gì?;
3. Practice;
4. Submit;
5. Results;
6. Review;
7. Next.

Important states are explicit:

- no onboarding: invite setup or continue neutrally;
- no diagnostic: offer baseline, not a fake level;
- insufficient evidence: explain what is missing;
- no active practice: show approved catalog;
- no mistakes: say the notebook is empty;
- pending AI/manual review: preserve the work and explain next action;
- offline/autosave conflict: show recoverable state.

The UI does not use hover-only information, does not conceal score disclaimers,
and keeps keyboard focus/ARIA semantics for timers, upload/audio controls,
filters, result actions, and mock navigation.

## 22. Testing

### Unit/service

- onboarding validation, skip/edit/versioning;
- diagnostic state, confidence, insufficient evidence, and no official-
  placement wording;
- Today's Plan cap, reason-code provenance, time budget, and neutral fallback;
- notebook grouping, repeated counts, acknowledgement, and resolution policy;
- Mock Test transitions, timer math, section order, resume/expiry, and
  duplicate submit;
- saved practice idempotency and deactivated-version behavior;
- profile update boundaries and preference reuse.

### Repository/controller/security

- every new row scoped to the authenticated owner;
- User A cannot access User B diagnostics, plan reasons, notebook, mock, saved
  practice, or profile;
- unapproved content cannot be saved or started;
- admin review/search data is not exposed;
- pagination and query limits are enforced;
- optimistic concurrency and idempotency return safe conflicts.

### Frontend

- onboarding resume/skip/edit;
- diagnostic step states and honest confidence labels;
- Today's Plan evidence reasons and empty states;
- notebook filters/actions and Tutor handoff;
- Mock Test timer, autosave, resume, section navigation, partial result;
- progress charts render real/empty data without invented values;
- search/save/profile/settings loading/error states;
- responsive 1440/1024/768/375 layouts, reduced motion, keyboard and screen
  reader semantics.

### Cross-module acceptance

- new learner completes onboarding, skips diagnostic, sees neutral plan;
- learner completes diagnostic and sees Estimated starting profile with
  confidence state;
- a real graded mistake appears in the notebook and informs a plan reason;
- learner retries and the existing adaptive policy updates only with trusted
  evidence;
- approved practice can be saved, started, submitted, and appears in history;
- a mock can be paused, refreshed, resumed, submitted, partially graded, and
  fully graded without duplicate results;
- all four skills preserve Phase 4 result boundaries;
- no fake score, fake STT, fake pronunciation, or official claim appears.

## 23. Migration Strategy

Do not assign exact Flyway versions in this design. After the final main branch
is frozen, allocate coordinated versions after the Phase 4 migration range.
All changes are additive:

1. add onboarding/diagnostic/mock/save structures and indexes;
2. deploy owner-scoped read/write services behind feature-safe routes;
3. backfill no fabricated learner goals, diagnostics, scores, or notebook data;
4. build read projections from existing trusted Phase 2/4 records;
5. verify ownership and aggregate counts in QA;
6. enable learner UI progressively;
7. remove no legacy columns until all dependent clients are migrated and
   evidence supports removal.

Legacy databases are not touched by this design task.

## 24. Risks

- self-reported goals may be mistaken for measured ability unless storage and
  copy remain separate;
- diagnostic content may lack Listening media or Speaking STT; capability
  states must stay honest;
- plan recommendations can become opaque unless every item has a reason code;
- a notebook projection can overstate weakness if it ignores confidence and
  recurrence policy;
- Mock Test state/timer recovery is vulnerable to duplicate requests and clock
  drift without server timestamps;
- search can leak private history if result indexing is not owner-aware;
- too many dashboard requests can degrade mobile performance without a summary
  endpoint.

## 25. Non-Goals

No payments, community/social features, mobile app, video classroom, official
IELTS scoring, automatic pronunciation band without real audio analysis,
unreviewed generated practice, microservice migration, or fabricated research
metrics are part of Phase 5.

## 26. Definition of Done

- onboarding is optional, editable, owner-scoped, and separate from evidence;
- diagnostic produces an Estimated starting profile with confidence states;
- Today's Plan has no more than five evidence-backed or honestly neutral items;
- Error Notebook uses real question/mistake evidence and preserves history;
- Mock Test is version-pinned, resumable, autosaved, idempotent, and explicitly
  non-official;
- Progress is data-driven with meaningful new-user empty states;
- search includes approved learning content and only the current learner's
  history;
- saved practices are owner-scoped and version-pinned;
- profile/settings reuse current auth/preferences without duplicate password
  storage;
- Phase 2 and Phase 4 remain the source of truth for adaptive/scoring logic;
- all APIs, security, performance, responsive, accessibility, and regression
  tests pass with external AI mocked;
- migrations are additive and future versions are coordinated after main is
  finalized.

## 27. Rulings

1. Onboarding is self-report, not evidence.
2. Diagnostics say `Estimated starting profile` and never imply official band
   placement.
3. Today's Plan is a bounded Phase 2 projection with a reason for every item.
4. Error Notebook does not erase evidence or permanently resolve a weakness from
   one retry.
5. Mock Test is IELTS-style and non-official; section scoring remains under
   Phase 4 authority.
6. Search exposes only approved content and the current learner's history.
7. Saved practices pin a visible published version.
8. Profile identity and preferences reuse the current auth/preferences model;
   no duplicate auth profile or password table is created.
9. No new AI provider router, adaptive engine, scoring engine, STT, or Tutor
   memory system is introduced.
10. All new entities and APIs are owner-authorized, paginated, and idempotent.
11. Phase 5 implementation is decomposed into 5A Onboarding + Diagnostic, 5B
    Today's Plan + Error Notebook, 5C Full Mock Test, and 5D Search + Saved
    Practice + Profile completion.
12. Safe future lanes are 5A/5B after Phase 4 contracts, then 5C, then 5D;
    integration occurs at submission/result, roadmap, catalog, and profile
    API boundaries.
